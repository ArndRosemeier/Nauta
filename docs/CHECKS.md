# Checks

Tests are only useful if they run all the time, so they stay fast, and the limits are enforced by the tools, not by good intentions (Arnd 2026-11-17: "I often had test suites run out of control").

## Time budgets

The numbers live in `tools/test/budgets.json`. **Raising one needs Arnd's OK**, written next to the number here with his name and the date.

| Limit | Value | What happens |
|---|---|---|
| One test | **2 s** | The run fails, naming the test. |
| One test file | **5 s** (its tests added up) | The run fails, naming the file. A test that hangs is stopped at 5 s (`--test-timeout`) and fails, naming it. |
| The whole of `npm test` | warns at **20 s**, fails at **30 s** | The run fails, on a desk as in CI. |
| A slow check (browser, screenshots, a long simulated fight) | warns at **2 min**, fails at **3 min** each | `tools/guards/budget.mjs` around the step in CI. |
| All slow checks together | **10 min** | The CI job's own limit. |

`npm test` is `node tools/test/run.mjs`: every `test/**/*.test.ts` (through tsx) and `tools/**/*.test.mjs` under Node's test runner. After each run it prints the five slowest tests and the suite's time against its budget, so creep shows long before a limit is hit. `npm test -- test/look.test.ts` runs the files given.

**How the runner runs them** (2026-11-18). The files are dealt in turn, in sorted order, into **three shards**, three processes side by side (`tools/test/shards.mjs`): the same list of files always gives the same shards, each file in the same place. A shard runs its files one after another in **one process** (Node's test isolation `none`), so the modules, tsx's compiling, the lazy tables (walk graph, rig plan, hull) and the JIT warm up once a shard rather than once a file. Until then each file had a process of its own, and about 60 % of the suite's time was that start-up repeated in every file: the 62 files took 47 s of processor time one by one, 19 s in a single process. A test's time and its file's are measured as before, and the budgets are the same. A test that hangs is stopped at 5 s by the test timeout and fails, naming it; a shard still running at the suite's 30 s (a test busy in a loop cannot be stopped by a timeout) is stopped and named, with its test or the files that never reported, and the other shards' results still print. The runner needs Node 22.8 or later (CI and `.nvmrc`: Node 24); an older Node runs each file in its own process and says so.

Files that share a process must not lean on each other, so **a test never changes module-level state that another file could see**: no setting of a shared module's variables, no globals, no environment. A module's lazily built, frozen table (a fixture or cache) is fine; a test that needs a changed rule builds its own state for the purpose. The slow-checks job guards this: it runs the whole suite the old way as well, each file in its own process (`npm test -- --isolated`, held only to a slow check's 3 minutes), and fails if any test fails there. A test that passes in its shard and fails alone, or the other way round, leans on another file.

What keeps tests fast:

- No browser, no network, no big simulation in `npm test`. Those are slow checks.
- Seeds, fake clocks and small fixtures, never wall-clock waits.
- A fixture several files need is built once and frozen, not once per test.
- A test that outgrows 2 s gets a smaller fixture or is split. It does not get a longer limit.

### Keeping the suite inside its 30 s as the game grows

The 30 s are for the whole game, through the last milestone, not for what exists today (design thread, 2026-11-18, after one night's packages took the suite on CI to 21 s). CI is up to twice as slow as a quiet desk, and slower again while test files run side by side. So:

- **Half the limit is the working limit.** `npm test` warns when one test passes 1 s or one file 2.5 s (`testWarn`, `fileWarn`). A thread treats a warning on its own files as a failure and fixes it before merging; a test at 1.5 s on a desk is a test that fails on CI by chance.
- **`npm test` checks rules, a slow check plays the game.** A test in `npm test` steps the simulation for at most 60 simulated seconds, and a test file for at most 5 simulated minutes in all. It proves a rule on the smallest case that shows it: one order, one gun, one hole, from a state built for the purpose. Whatever needs minutes of simulated time (heaving to until she stops, a tack from start to finish in a seaway, a crew carrying out every order, a whole fight) is a scenario in that area's slow check (`check:sailing`, `check:replay`, and one more per area as it comes), where it joins the scenarios already there and does not get a script of its own.
- **A package's share.** A work package adds at most about 1 s of test time to the suite on a desk (the sum of its tests as the run prints them). One that needs more moves scenarios to its slow check.
- **The suite's warning is a stop sign.** While `npm test` on CI is over its 20 s warning, nothing that adds test time merges; the first job is to bring it back under, starting with the slowest files the run lists.
- Fixtures are built once per file and frozen (a rig plan, a ship plan, a sea), never once per test.

### Timing tests

A test never asserts bare milliseconds: a CI runner is slower than the tablet and shares its cores with the other test files, so such a test fails by chance and gets flakier as the suite grows. A test that guards a cost uses `pace(work, pairs)` from `test/support/pace.ts`: the work's time as a share of a reference loop of plain sines and cosines, measured in the same rounds on the same machine. The limit is then a ratio that holds on any machine. The milliseconds themselves (a sea sample, a simulation step, a frame) are measured where they count, on the tablet, by `?bench`.

## Slow checks

Each is its own script, run in CI on pushes to `main` (the three `Slow checks` jobs) and by hand, never inside `npm test`.

- `npm run check:shots [-- <out dir> [start|sea]]`: the browser checks of CI, the built game in headless Chromium (tools/shot/check.mjs), as **two checks, each on its own page load** and each its own CI step: `start`, the desktop view as it starts (1280 × 800, with the HUD), then the view changed to a tablet in landscape (1180 × 820), a finger dragged across it and the scene drawn again; `sea`, 6 of the standard sea shots from her quarterdeck, every time of day and every sea once (`CI_SHOTS` in the script; see `shot:sea`), at `quality=high`, and their sheet. With neither named both run, one after the other. Each fails if its page throws or never gets ready (then at once, after a picture of what is there; CI sets `SHOT_TIMEOUT` so that happens inside the step's 3 minutes). It draws with WebGPU on the software GPU (SwiftShader): that GPU computes and renders but cannot present to a canvas (the device is lost on the first frame), so the browser scripts inject a stand-in swap chain (`tools/shot/swapchain.js`) that renders into a plain texture, paints the last frame into the canvas for the picture, and paces the page's frames to the GPU as a real swap chain does (without that the page queues 60 frames a second while the software GPU draws one or two, and a picture taken later waits minutes for them). `SHOT_GPU=1` uses the machine's own GPU and presents normally. Software frames are slow (seconds at 1280 × 800), so their times say nothing about the tablet. CI runs them in Playwright's own Chromium (installed and cached in the job), not the runner's Chrome: with the runner's Chrome the page took 98 s to get ready, with Playwright's Chromium 59 s. On one page the two took 131 to 199 s on CI (2026-11-18), past the 2 minute warning and once past the 3 minute limit, so they were split; then the page's start was cut (see "Browser checks: the rule" below). CI keeps the pictures as the run's `shots` artifact.
- `npm run shot:glass [-- <out dir>]` (N3.8), by hand, not in CI: the duel sailed alone on one page, the match run on only by the check (`__nautaSail.onward`): the other brig at the start with the naked eye and through the glass at 10 and 20 times, through the glass as she closes to 800 m, with the naked eye as her whole outside crossfades in (about 160 m), and alongside from above and from her bowsprit. Prints her triangles, whether she is drawn near and the frame's draws; fails if the page throws, she is missing or she is never drawn near. About 4 minutes in the cloud.
- `npm run shot:guns [-- <out dir> [larboard] [dusk] [foe] [half]]` (N5.4a, N5.5), by hand, not in CI: a broadside on one page of the duel sailed alone (seed 1, force 3), run on only by the check: her guns housed, then at quarters held for the word, the other brig brought abeam and the word given; the flash through the port, the whole side firing from 50 m off, the gun leaping back, the fall of shot about her through the glass, then her smoke hiding the other brig from her rail and clearing over half a minute. `larboard` fires the other side, running before the wind after the two have passed; `dusk` at 20:00; `foe` the computer captain's broadside received instead. `half` draws the smoke at half resolution (`?smoke=half`). Fails if the page throws or no broadside comes. About 3 minutes in the cloud (4 with `larboard`).
- `npm run shot:ui [-- <out dir>]` (N7.0, N7.3), by hand, not in CI: the interface's sheets on the plain sea page (one page start): the view with the compass rose, every page of the settings, the sound page in German, what's new over the settings, and the settings upright on a tablet and at a phone's width (tools/shot/ui.mjs). Fails if the page throws. About a minute in the cloud.
- `npm run shot:title [-- <out dir>]` (N7.7), by hand, not in CI: the title alone (`?title`) at desktop, tablet and upright tablet sizes, the sun dragged to dusk and to the afternoon, and a tap on the brig (her flash, her smoke, the other brig's answer); prints how long its first picture took. About 40 s in the cloud.
- `npm run shot -- "<query>" out.png`: the built game at any address, a page load per picture, for looking by hand (see the script's header for its switches: SHOT_SIZE, SHOT_DRAG, SHOT_WAIT).
- `npm run check:replay` (N3.1): ten simulated minutes of a duel in the strongest wind, two brigs under a seeded script of orders, run in two processes side by side and once more with the state sent through bytes and back at five minutes; fails unless all three have the same hash at every simulated second. About 6 s (two runs of two ships for ten minutes are more than a test file's 5 s).
- `npm run check:sailing` (N3.3): the brig sailed through whole matches (sea, gusty wind, sailing and floating) in every wind from force 2 to the gale, under battle and plain sail: prints her speed close-hauled, on the beam, on the quarter and before the wind, her steadiest heel, how long a tack from a beam reach takes (from the helm put over) and how long heaving to takes her way off (N3.4); fails if a state stops being a number, a steady heel passes `HEEL_LIMIT`, a tack from force 3 up takes a minute or more, heaving to from force 3 up has not taken her way off in five minutes, or the fresh breeze's speeds stray from the table (rules/sailing.ts) by more than one and a half times the test's tolerance. Then the orders as the captain gives them (N3.4, N3.5), each first checking she was under way as it names: a course on the other tack reached by wearing with the master saying so, a course 30° off the wind steered full and by instead, a tack in a fresh breeze through the wind only after the hands are at their stations and full and by on the other tack, heaving to in a fresh breeze still within two minutes and lying within a knot of still, filling back to battle sail and way, and the order panel's eight compass points from a start under way each reached or answered full and by. Last her roll on the sea, moved here from `npm test` for its simulated minutes (2026-11-18): ten minutes of floating in the strongest preset, her heading swinging round, never blow up (roll under 40°, pitch under 25°, heave under 8 m) and the gale does move her; under all the sail the crew will carry in it, on the beam and close-hauled, her mean heel stays under `HEEL_LIMIT`; and in a force 5 beam sea battle sail steadies her roll against bare poles (bare poles roll her past 12°, battle sail swings her less than 0.7 times as far, heeled to leeward). About 35 s.
- `npm run check:crew` (N4.1): the crew carrying out the captain's orders to the end. Every order the crew works for, done by a full crew driven alone: each job has all its hands, works the time in the table (rules/crew.ts `JOBS`) and none is short-handed. Every order of the vocabulary in a whole match, carried out and reported done in no less than a second and within a minute. Plain sail in a whole match, the courses and topgallants set one by one, each no sooner than its men have loosed and sheeted it home, then taken in again by battle sail from half set. Two brigs whose crews make plain sail at once stay under the network's 16 KB a state through the whole manoeuvre, and the busiest state, sent through bytes, steps on to the host's hash. Prints each order's time and the state's peak; fails if a scenario does not hold or did not do what it names (fewer orders done, sails set or men walking at once than it sets out to have). About 3 s.
- `npm run check:gunnery` (N5.2): two brigs lying broadside on in a force 4 sea at 100, 200 and 400 m, five seeded runs of two minutes at each; one's starboard battery, full-crewed, loads round shot, lays on the other's hull and fires as they bear, and each ball's path is traced through her side (a stand-in for N6.1's hits). Prints the share that strike her and how far chain and grape carry; fails if a share strays more than 0.1 from the design's (3 in 4, half, 1 in 5), or if the check did not do what it names: fewer than 60 shots at a range, her roll swinging less than 2°, a path or pose not a number. Then the `?sail` match's broadside by the panel's words (N5.3a): from the duel's start the first ship bears away to bring the enemy abeam, beats to quarters and holds for the word, and once her starboard guns stand ready the word is given; fails unless the first gun fires at the word's tick and every gun that fires is of that side, has its flight and fires within the ripple. About 12 s.
- `npm run check:captains [-- <duels>]` (N7.1): computer captains fight whole duels against each other, from the duel's start (`duelStart`, a seed each) to the end, each duel in a process of its own, as many at once as the machine has cores (`tools/sim/captains.ts`). CI fights 8 (the six pairings of the three skills in turn, then two more); `-- 24` fights more by hand. A duel to nightfall costs about 40 s of a core (about 0.5 ms a step with both crews fighting), so 100 duels would take about 17 minutes on CI's four cores: the 100 of the plan are a hand run. Fails on what the captain owns (design thread, 2026-11-18): a duel not over at nightfall, ships that never came within 600 m or a ship that never fired, a beaten ship that did not strike within 20 s, any order of his refused, a pose not a number. Prints the balance sheet beside it, which it does not fail on (N7.5 meets it): each duel's skills, force, length, how it ended and who won, the closest the ships came, guns fired, hits, men out, water, spars fallen, the state's peak size and the cost of a step; then how many were drawn and how many won within 10 to 20 minutes. About 90 s on four cores, in a CI job of its own (it takes every core).
- `npm run check:room` (N3.7): two headless browsers play one match through GameHub (`tools/net/room.mjs`, the pages are `?netcheck`, the match without drawing, so no GPU is needed): one opens a room, the other joins by its code, both give orders; fails unless they agree on the hash at every second both reached, the guest never drifted, each order was carried out for its captain's ship, and the guest takes over and runs the match on when the host's page closes. Without `GAMEHUB_URL` it plays through a stand-in on the machine (`tools/net/standin.mjs`, GameHub's wire protocol over its own WebSocket), since the cloud container cannot reach the live server; `GAMEHUB_URL=https://games.futuremagic.de` plays against the live one with the game's own key (CI does both). About 15 s.
- `npm run check:ship [-- <out dir> [all | words...]]` (N2.5): the brig sailed by a match (`?sail&seed=4`: the duel's start, on the beam under battle sail, force 6) on a page of its own (tools/shot/ship.mjs): she sails 30 s so her wake lies behind her, then the pictures: CI takes three, over her rail (the water along her side), from above (her wake) and from her berth deck (no water inside her); `all` adds her bowsprit, astern along her wake and 50 m off, each scene set with `window.__nautaScene` (`ship=`), and last the other brig's wake: the match run on with `onward` until the two have closed and passed, then her seen through the glass from above her own ship. The match keeps its own clock, so she sails on between pictures and they differ a little from run to run. Fails on any error or warning on the page, or when a scene leaves the picture unchanged. With all six it took 104 to 145 s on CI (2026-11-18), a frame of the whole ship costing 8 to 16 s there; with three, about 80 s in the cloud. It stays the tightest of the browser checks: a picture more goes into the hand-run set.
- `npm run shot:sea [-- <out dir> [words...]]`: the standard sea shots (plan N1.9), dawn, noon, dusk and a moonlit night × calm, breeze and gale × eye at 4.5 m (her quarterdeck) and 30 m (her masthead), looking into the sun or moon, at quality `high`, with the clocks stopped so the same waves come back every run; and `sheet.png` with all 24 on one page. One page sets each scene in turn (`window.__nautaScene`), so the shaders are built once. The whole set is for looking and runs by hand; CI takes 6 from the quarterdeck in `check:shots`'s `sea` check. Drawn at 800 × 500 (SHOT_SIZE sets another size). Words pick a part of the set (`npm run shot:sea -- shots/sea noon gale`).
- `npm run shot:sails [-- <out dir> [all]]` (N3.10): the brig's sails on one page (`?sail`, tools/shot/sails.mjs), commanded through `window.__nautaSail` and run on by whole minutes at once: CI takes the beam under all sail, in stays (a sail aback), being clewed up and furled; `all` adds every point of sail, the view from the quarterdeck and the far ship's from 2 km. Fails unless the sails were drawn as each step names. The match moves only by the check's jumps and the page holds between pictures, so each picture costs one frame and shows the same moment on any machine. In the cloud: CI's set about 50 s, `all` about 90 s.
- `npm run shot:probe [-- "<query>" [<width>x<height>]]`: where a page's time goes on the software GPU (tools/shot/probe.mjs): opens the game at `query` (default `?day=0&quality=high`, 800 × 500) as the checks do and prints how long it took to get ready and to draw two frames more, the pipelines built (how many, their summed time, the slowest) and the queue submits that kept the GPU busiest, with their passes, draws and first-used pipelines. A submit of seconds before the page is ready means something draws whole frames behind the loading screen.

**A slow check proves it did what its name says** (2026-11-18). The walk check once stopped walking in its heavy sea without failing: a changed argument made the ship's pose not a number, and every comparison with it passed. So a check asserts its own conditions before its result counts: the sea was as rough as named (she rolled at least so far), the ship moved, the walker covered every space, no state stopped being a number. A check that cannot fail is worse than none. `tools/` is type-checked with the rest (`npm run build`), so a changed signature is found there too.

**Browser checks: the rule** (2026-11-18). On CI's software GPU a browser check costs its page's start and one frame for each picture, and nothing else may cost. A frame of the whole view takes seconds there (the sea alone about 4 to 6 s on CI, the brig 7 to 10 s), so:

- **The page's start is short: whatever warms up behind the loading screen draws one pixel.** The shared stage builds every shader before the first frame, and its shadow warm-up used to draw the whole scene eight times to do it: half a minute or more of GPU work behind the loading screen, with the shader builds after it waiting their turn. On slow runners the brig's page took 60 s to get ready. Since 2026-11-18 those draws run under a 1 × 1 scissor (`drawOnePixel` in `@futuremagic/stage`). The same shaders are built, but the sea page's first picture comes after about 22 s in the cloud instead of 48. Anything new that must be drawn to warm up goes through the stage's warm-up, never as whole frames. `npm run shot:probe -- "<query>"` shows a page's start.
- **One frame for each picture: the page holds between pictures.** A check sets its scene with `window.__nautaScene` or runs the match on with `window.__nautaSail.onward`. Each draws one frame and then holds the page, so no frame is drawn while the check gets the next picture ready. A picture taken while frames keep running waits for the frame in flight as well: two frames. That is what took the sails check past its 3 minutes on CI.
- **The check sets the clock, not the wall.** A match a check runs on moves only by the check's jumps (`onward` stops the page's clock), so every picture shows the same moment on a fast runner and a slow one, and a step's settle time holds everywhere. A wall-clock wait costs its full length on every run, and each runner draws a different number of frames in it. Use one only where frames must be drawn over time: `check:ship` lays her wake over 30 s of drawn frames, because jumps of the clock left a thinner wake (and, in steps of 15 s, a white streak along her track).
- **A new check's budget: its page's start plus its pictures within 90 s on a slow runner.** Count 30 s for the start and a frame for each picture (10 s with the brig, 6 s for the sea alone). That keeps a slow runner under the 2 minute warning. Pictures of a page that is already loaded join that page's check while the check stays within 90 s. A page that cannot be shared is a check of its own, with its own CI step and its own 3 minutes.
- **CI takes the part of a set that guards something.** The whole set is for looking and runs by hand. Of the 24 sea shots, CI takes 6 from the quarterdeck, every time of day and every sea once. Of the sails' pictures it takes 4, of the ship's 3.
- **Each slow job's checks together stay within two thirds of its 10 minutes, measured on main's slow runs.** The slow checks run in three jobs side by side (`.github/workflows/ci.yml`): the start, the sea and the simulation in one, the brig in a browser (the ship, her sails) in another, and the computer captains' duels (`check:captains`, which takes every core) in a third with no browser. Each job gets its own 10 minutes. The two with browsers share their setup (`.github/actions/slow-setup`). A new check goes into the job with more room. Each job's last step (`budget.mjs --sum 600`) prints its sum: every step that `budget.mjs` timed adds itself to `BUDGET_LOG`, and the step warns past two thirds, as a single check does. A check past its 2 minute warning is cut back before anything is added to it.
- None of this changes a limit.

Real frame times are measured on the tablet, not in a check: open the game with `?bench` (`?bench=30` for a shorter flight). It flies a fixed path for 60 s (a brig's waist up to her masthead and down, turning round twice) and shows the frame time's median, 95th and 99th percentile and worst, the share of frames on time (none missed the display's refresh: at most 1.5 × 16.7 ms), the frames over 33 ms, the page's own work per frame, GPU memory as three.js counts it and the script heap where the browser tells it (Safari does not). It sets the scene like any page: `?bench&sea=gale&hour=17.7`; with `?slice` it measures her slice from the standpoint, without the flight.

## Guards

Part of `npm test` (`test/guards.test.ts`); `npm run guards` prints them alone.

- **Layers** (`tools/guards/rules.json`): the pure layers (`src/sim`, and the pure files of `src/app`) import no three.js and nothing from `src/render`.
- **No `Math.random`** anywhere under `src`.
- **Change-friendly rules** (`tools/guards/discipline.mjs`, [ARCHITECTURE.md](ARCHITECTURE.md)): no bare number under `src` (only 0, 1, 2 and indexes; everything else is a named top-level constant); a field of the game's state is assigned only in its owner file (`owners` in `rules.json`); every row of [SEAMS.md](SEAMS.md) points at an export that exists.
- **Duplication ratchet** (`tools/guards/duplication.mjs`), on every run:
  - A copied function body (two functions alike enough to be one) is **never allowed**. Keep one and call it from both places.
  - A repeated idiom (the same few lines in three files or more) or two alike functions of one name must be listed in `tools/guards/duplication-baseline.json` with a reason: a false alarm says why it is one, a real copy needs Arnd's OK. `npm run guards -- --keys` prints the entries to fill in.
  - A listed entry that is no longer found fails as stale, so the list only ever shrinks to what is true.

`npm run dup` and `npm run repeated` (the Toolbox finders behind the ratchet) write full reports to `reports/` for a closer look, including weaker candidates the ratchet does not fail on.
